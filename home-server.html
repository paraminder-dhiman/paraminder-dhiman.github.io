Home Server and Automation

Infrastructure · Unraid, Docker, Python · 2026

    A home server I designed, built and run for friends and family. It streams media, signs people up through a Discord bot I wrote, and backs itself up every week.

    I did all of it myself, from the hardware and the network to the containers and the code. It started as a way to learn how networking works, and it turned into a small service that people use every day.

    • 4 user tiers
    • 3 copies of every backup
    • 7 weeks of backups kept
    • 0 ports open to the internet

    How it fits together

    People come in through a Cloudflare Tunnel or through Discord. Admin access is over Tailscale only.

    What runs on it

    Hardware

    A Ryzen 9 5900X with 64 GB of RAM and an RTX 2070 Super, which handles video encoding in hardware. How it moved here from a small office desktop is further down.

    Platform

    Unraid, with every service in its own Docker container. App data sits on an NVMe cache and the library on a four-drive array.

    Media streaming

    Jellyfin with four user tiers. Each tier sets a bitrate cap, a session limit and whether group watching is allowed.

    Library preparation

    A Tdarr pipeline runs on the graphics card. It re-encodes the library and health-checks every file, so most devices play files directly and the server rarely has to transcode.

    Network

    AdGuard Home filters DNS and is also the network's DHCP server, so every lease lives in one place.

    Remote access

    Public services go out through Cloudflare Tunnels. Anything administrative is reachable over Tailscale only.

    Monitoring

    Uptime Kuma watches the services, and a speed test tracker logs the connection over time.

    Power

    My workstation stays off unless it's needed and is woken over the network when it is.

    Housekeeping service

    A second Python service, written from scratch, whose main job is to move finished files from the server to my workstation without ever losing one.

    It runs in its own container with its own repository, and works on a loop: every few minutes it checks each job, moves what's ready and reports what it did.

    1. TagTen minutes after a job arrives, it gets a destination: the workstation by default, unless I've already set one by hand.
    2. ReleaseWhen the job meets its release condition, the service pauses it, moves its files to a ready folder and clears the job.
    3. Pick upA scheduled script on the workstation copies each file across, checks it with a SHA-256 hash, and only then deletes the original.
    4. ReportEvery action is posted as one line to a private Discord channel through a webhook.

    Tidying up

    Empty folders are removed on a timer, and leftovers older than three days are cleared out.

    Backup watch

    It raises a flag if no backup has run in eight days.

    Weekly digest

    Once a week it posts a health report: backup age and copies, disk use, CPU and NVMe temperatures, what's waiting in each ready folder, and the week's counts.

    Why it works this way

    Pause before moving

    A file that's still being written can't be moved half-finished.

    Copy, verify, then delete

    Every hop checks before it deletes, so no step removes anything it hasn't confirmed arrived.

    Dry run first

    Cleanup starts in dry-run mode. New deletion rules prove themselves in the logs before they touch a file.

    Alerts once a day

    A problem is reported at most once a day, so a missing backup drive doesn't flood the channel every five minutes.

    Async Python

    Built on aiohttp, so several services can be checked in one cycle without one slow reply holding up the rest.

    The Discord bot

    Everyone who uses the server is in one Discord server, so I wrote a bot to run the front desk. It's Python with discord.py and slash commands. Each feature is its own module, loaded automatically at start, and the bot runs as its own container. It talks to the other services over the local network, never through their public addresses.

    Onboarding

    1. RequestA new member gets a guest role and a Request access button.
    2. ReviewThe request lands in an admin channel with Approve, Approve as trusted and Decline.
    3. AccountApproving creates the streaming account on the right tier and swaps the member's role.
    4. LoginThe login details arrive in a direct message. Declining sends the reason instead.

    Requests

    1. AskA member searches for a title and picks it from its posters, with a season picker for shows.
    2. FileThe request is filed under the member's own account, not the bot's.
    3. ApproveAdmins approve or decline it from a queue.
    4. ReadyThe member is tagged in Discord when it's ready to watch.

    Accounts

    Creates streaming accounts with the tier's limits applied, and keeps a JSON map between Discord members and their accounts.

    Library

    Commands for library stats, search and what was added recently.

    Server stats

    A hardware command shows GPU load and temperature from the graphics driver, and CPU power from the processor's energy counter. Containers can't see that counter, so it's passed in as a single read-only file.

    Held back on purpose

    A strike system is fully designed, from a warning to an automatic disable that expires after 30 days, but it waits until the server is big enough to need it. Storage warnings were dropped because the platform's own alerts already cover them.

    Code

    Kept in a private Git repository. Secrets and data files stay out of version control.

    Backups

    App data and the boot drive are backed up once a week, on Saturday mornings, when I'm home to fix whatever breaks. Seven backups are kept, which covers the last 50 days. I chose weekly over daily because only a few people use the server on any given day.

    1. Flash driveThe weekly backup is written here first.
    2. Second driveThen copied to another drive in the server.
    3. WorkstationAnd copied again to my workstation.

    Design decisions

    Nothing is open to the internet, and everything the server does is written down where I can read it.

    Keeping it safe

    No open ports

    Nothing on the router is opened to the internet. Public pages go out through Cloudflare Tunnels, and admin access is over Tailscale only, so there's nothing to scan or attack from outside.

    Lockout after three tries

    Accounts lock after three wrong passwords, which stops password guessing without running a separate blocking tool.

    One place for the network

    AdGuard Home is also the DHCP server, so every device's address and every DNS rule live in one place instead of being split with the router.

    Keeping it running

    Back up, then update

    Apps update themselves, but only straight after the weekly backup, so an update that breaks something can be rolled back to that morning.

    Clean shutdowns

    A UPS tells the server when the power goes out, and it shuts itself down cleanly instead of risking the array.

    Logs that survive a crash

    A syslog server keeps the system log, so a crash's last messages are still there after the reboot.

    Checked every minute

    Every service is checked once a minute, so problems show on a status page before anyone using it notices.

    Tiers that share fairly

    Each tier caps bitrate and sessions, so a few people streaming at once never slows it down for everyone else.

    Encode once, direct play everywhere

    The library is re-encoded once to a format almost every device plays directly. That costs a one-off pass on the graphics card, but means the server rarely transcodes while people watch.

    Keeping it simple

    Separate services

    The Discord bot and the housekeeping service are separate programs, each in its own container and Git repository. Media-facing jobs go to the bot, and jobs between machines go to the housekeeping service, so one can break or restart without the other.

    Logs you can read

    Every automated action is posted as a single line to a private channel, so I can see what happened without opening a terminal. Noisy events are left out on purpose.

    Moving to new hardware

    The server started on a small office desktop. Moving it meant planning around people who use it every day.

    1. PlanA Ryzen 9 5900X, 64 GB of RAM and an RTX 2070 Super, built partly from parts I already had. One memory stick had once failed a test, so every stick was checked.
    2. Prove it aloneThe new machine was built and stress-tested on its own first, with three full MemTest86 passes before anything moved.
    3. Move at onceThe boot drive, the cache and every array drive moved across in one step, so the server only went down once.
    4. Fix what brokeThe new board's security chip changed how the licence is tied to the hardware, and the array wouldn't start. Replacing the key wrote an empty file, and recovering it fixed that. A device limit then blocked the array, solved by upgrading the licence.

    The server was back the next day on the new hardware with nothing lost, and video encoding moved to the graphics card.
